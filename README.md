# Маршрут — прототип сервиса с планом продвижения

Веб-приложение, которое по короткой анкете собирает для владельца малого/среднего
бизнеса персональный пошаговый план продвижения и привлечения клиентов из интернета.
Инструкция формируется **не через ИИ**, а через движок правил, который комбинирует
готовые экспертные модули в зависимости от ответов — это предсказуемо, дёшево в
эксплуатации и легко улучшать вручную.

## Админ-панель — `/admin`

Отдельная страница для владельца сервиса, не привязанная к общей навигации
(ссылки на неё нет ни в шапке, ни в футере — только прямой переход по адресу).

**Прежде чем показывать это клиентам или коллегам, два важных ограничения:**

1. **Пароль не является настоящей защитой.** Это код на фронтенде
   (`ADMIN_PASSWORD` в `app/admin/page.tsx`), он виден любому, кто откроет
   исходный код страницы в браузере. Сейчас это просто заслон от случайного
   захода. Перед реальным использованием нужно закрыть `/admin` серверной
   аутентификацией с проверкой роли — например, через NextAuth с полем `role`
   у пользователя, либо Basic Auth на уровне Vercel/сервера.
2. **Вкладка «Пользователи» и цифры в «Выручке» показывают демо-данные,
   а не реальных людей.** Это не заглушка «для вида», а следствие текущей
   архитектуры: у сервиса нет общего бэкенда, каждый посетитель хранит свои
   данные только в своём собственном браузере (`localStorage`). Из браузера
   администратора физически нет доступа к данным других людей, пока не
   появится сервер с базой данных, куда будут писать все клиенты сразу. Вкладка
   сделана так, чтобы показать, как будет выглядеть и фильтроваться этот экран
   после подключения БД (`lib/adminMockData.ts` — заменить на реальный запрос).

**Что при этом по-настоящему работает уже сейчас:**

- **Вкладка «Модули плана»** — реально управляет содержимым, которое получают
  пользователи в этом браузере. Можно отредактировать текст любого встроенного
  пункта (название, объяснение «почему это важно», шаги, срок до результата) и
  сбросить его к исходному варианту; можно добавить полностью новый пункт с
  собственным приоритетом и списком типов бизнеса, для которых он показывается.
  Формулу скоринга у встроенных пунктов через форму не поменять осознанно — это
  сложная логика в коде (`lib/modules.ts`), которую нельзя надёжно свести к
  простой форме, не потеряв в качестве рекомендаций; для новых пунктов вместо
  этого используется простое правило «приоритет + список типов бизнеса»
- **Фильтр по тарифу** во вкладке «Пользователи» — реально фильтрует (пусть
  пока и демо-список), интерфейс останется тем же и после подключения бэкенда
- **Вкладка «Сообщения»** — реально сохраняет переписку. Пользователь пишет в
  поддержку из личного кабинета → сообщение действительно появляется в этой
  вкладке; ответ администратора действительно появляется в личном кабинете
  пользователя. Ограничение то же, что и у остальных данных: это работает,
  только если пользователь и админ находятся в одном браузере (например, вы
  тестируете сами себя) — для доставки сообщений реальным людям на их
  устройства нужен бэкенд, который будет хранить переписку на сервере, а не
  в `localStorage` (`lib/support.ts` — на что заменить при переходе на бэкенд)

## ⚠️ Отдельно про политику персональных данных

Страница `/privacy` заявляет, что данные пользователей хранятся на серверах
на территории России и не передаются третьим лицам. **Прямо сейчас это не
факт, а описание целевой архитектуры**: в этом прототипе нет вообще никакого
сервера — все данные (email, профиль, подписка, сообщения) физически лежат в
`localStorage` браузера каждого посетителя, и никуда с его устройства не
уходят просто потому, что отправлять их некуда.

Это значит: пока вы не разверните настоящий бэкенд с базой данных на
российском хостинге (см. рекомендации в разделе про 152-ФЗ ниже) и не
подключите к нему Сервис, публиковать эту страницу как достоверное
юридическое заявление о том, где хранятся данные, нельзя — формально это
будет недостоверная информация, что уже вопрос не UX, а закона. Как только
бэкенд появится и данные пользователей реально переедут на сервер в РФ — текст
страницы сразу станет фактически верным, менять в нём ничего не придётся.

## Что уже готово в этом прототипе

- Удаление аккаунта в личном кабинете (с подтверждением) — стирает профиль,
  подписку, все бизнесы и переписку с поддержкой для этого email. В админке
  на вкладке «Пользователи» есть похожая кнопка у демо-пользователей, но она
  убирает строку только из текущей сессии просмотра (без сохранения) — это
  тот же демо-список, что и везде в админке, см. предупреждение выше
- К сообщениям в техподдержке (и в ЛК, и в админке) можно приложить картинку:
  сжимается на клиенте до ≤1200px и сохраняется как часть сообщения
  (`lib/imageUtils.ts`, `components/ImageAttachField.tsx`) — реально работает
  в пределах одного браузера, как и вся система сообщений

- Политика обработки персональных данных (`/privacy`) — заявляет хранение
  данных на серверах в РФ и запрет передачи третьим лицам (кроме платёжной
  системы для проведения оплаты и случаев по закону). **Важно:** сейчас это
  описание целевой архитектуры, а не факт — см. предупреждение ниже
- Попап согласия перед оформлением любого тарифа теперь требует согласия сразу
  с договором оферты и с политикой персональных данных (два отдельных линка,
  одна галочка)
- Двусторонние сообщения между личным кабинетом и админкой (`lib/support.ts`):
  пользователь пишет в поддержку из ЛК → сообщение реально появляется во
  вкладке «Сообщения» в админке; админ может ответить или написать
  пользователю первым, выбрав его из таблицы пользователей. Работает только
  в пределах одного браузера — подробности в разделе про админ-панель

- Логотип «Ключевое слово» подключён из присланного файла: компактная марка
  на мобильных (`public/logo-mark.png`), полный лого-блок с подписью
  «Маркетинговое агентство» от планшетов и выше (`public/logo-full.png`), и
  фавикон вкладки браузера (`app/icon.png`), автоматически нарезанные из
  исходного файла
- Договор публичной оферты (`/oferta`) с реквизитами ИП и разделом, ещё раз
  закрепляющим информационный/рекомендательный характер сервиса (раздел 4) —
  текст один и тот же в `lib/offer.ts`, ссылки на него из футера, из блока
  «Ограничение ответственности» и из попапа согласия при оформлении тарифа
- Лендинг с объяснением продукта
- Анкета из 7 вопросов (мастер по шагам)
- Движок правил (`lib/ruleEngine.ts`), который на основе ответов собирает план из
  11 модулей (`lib/modules.ts`), сгруппированный в 3 этапа: фундамент → трафик →
  удержание клиентов
- UI результата: раскрывающиеся карточки с шагами, объяснением «почему именно это»
  и ориентиром по срокам
- Секция кейсов — 6 карточек в горизонтальном слайдере со стрелками прокрутки
  (свайп на мобильных работает нативно через скролл)
- Секция тарифов (4 плана, включая бесплатный пробный) — пока без реального приёма оплаты
- Форма заявки «Если остались вопросы» под тарифами — сейчас ничего никуда не
  отправляет, только показывает подтверждение на экране (см. следующий раздел)
- Блок «Ограничение ответственности» на странице и попап с этим же текстом и
  чекбоксом согласия перед оформлением любого тарифа — кнопка «Оформить
  подписку» внутри попапа неактивна, пока не поставлена галочка
  (`lib/disclaimer.ts` — единый источник текста для обоих мест)
- Мобильная адаптация: шапка с иконкой личного кабинета вместо текстовой
  ссылки на узких экранах, полноширинные кнопки и перенос строк в плотных
  местах интерфейса, уменьшенные отступы и размер заголовка хиро на самых
  маленьких экранах (проверено от ~320px)
- В личном кабинете видна дата окончания оплаченного периода. При отмене
  автопродления доступ к тарифу сохраняется до конца уже оплаченного периода
  (30 дней от активации), дальше аккаунт автоматически откатывается на тариф
  «Пробный» — это учитывает и анкета (лимит бизнесов и видимость этапов)
- Обязательная "регистрация" по email перед стартом анкеты (сейчас — мок на
  `localStorage`, без реальной проверки почты и без бэкенда)
- Ограничение пробного тарифа: после анкеты видно только 2 из 3 этапов плана,
  третий — заблокирован с призывом оформить подписку. На тарифах «Старт»,
  «Бизнес» и «Команда» видны все 3 этапа (`lib/plans.ts`, поле `fullPlanAccess`)
- Кнопка «Скачать PDF»: реально работает через системный диалог печати браузера
  (Ctrl/Cmd+P → «Сохранить как PDF») — это сделано намеренно, а не как временная
  заглушка: PDF-библиотеки для JS (например, jsPDF) без встраивания отдельного
  шрифта не умеют печатать кириллицу, а нативная печать браузера отображает
  кириллицу корректно
- Кнопка «Получить PDF на почту» — интерфейс есть, но реальная отправка письма
  требует бэкенда (см. раздел ниже), сейчас она предлагает сохранить PDF тем же
  способом и честно поясняет пользователю, что доставки на почту пока нет
- **Личный кабинет** (`/account`): данные профиля (имя, телефон), карточка
  подписки со статусом и кнопкой «Отменить/Возобновить подписку», список своих
  бизнесов с удалением
- **Лимит бизнесов по тарифу** (`lib/plans.ts` → `businessLimit`): «Пробный» и
  «Старт» — 1 бизнес, «Бизнес» — 3, «Команда» — 5. Перед анкетой сервис
  спрашивает название бизнеса и проверяет лимит; при превышении показывает
  экран с призывом освободить слот в личном кабинете или сменить тариф
- Нажатие «Оформить подписку» в прайсинге переводит аккаунт на выбранный тариф
  в демо-режиме (без реального списания денег) — это позволяет проверить всю
  логику лимитов и доступа к этапам без готовой платёжной интеграции

## Чего пока нет (следующие шаги)

1. **Настоящая аутентификация** — сейчас email только сохраняется в
   `localStorage` браузера, без подтверждения и без сервера. Нужен реальный
   вход (например, магик-ссылка на почту через NextAuth) и привязка тарифа
   пользователя к его аккаунту в базе данных вместо `localStorage`
2. **База данных** для хранения пользователей, анкет, бизнесов и статуса
   подписки — сейчас всё это в браузере пользователя и обнуляется при очистке
   данных сайта или смене устройства
3. **Реальный приём оплаты и управление подпиской** (см. ниже) — кнопка
   «Оформить подписку» должна вести на страницу оплаты ЮKassa, а не сразу
   активировать тариф
4. **Хранение самого плана**, а не только названия бизнеса — сейчас в личном
   кабинете виден список бизнесов, но повторно открыть уже сгенерированный
   план нельзя, можно только создать новый (в рамках лимита тарифа)
5. **Отправка PDF на почту** — серверный маршрут, который рендерит PDF (например,
   через Puppeteer/Playwright — они корректно работают с кириллицей, в отличие
   от jsPDF) и отправляет его через email-провайдера: из российских вариантов
   подойдут Unisender Go, Mailganer или SMTP от самого ЮKassa/CloudPayments
   личного кабинета
6. **Даты периода подписки сейчас считаются на клиенте** — `currentPeriodEnd`
   хранится в `localStorage` и легко подделывается через консоль браузера; в
   бою эту дату должен считать и проверять сервер при каждом обращении к
   защищённым данным, синхронно со статусом от платёжной системы
7. **Обработка формы «Если остались вопросы»** — нужен серверный маршрут
   (`app/api/contact/route.ts`), который отправит заявку в Telegram-бот или на
   почту и сохранит её в базе, чтобы не терять обращения
8. **Защита `/admin` серверной аутентификацией** и перенос демо-данных
   пользователей/выручки на реальный запрос к базе (см. раздел про админ-панель
   выше — это самое важное, что нужно сделать до реального использования)
9. **Хранение картинок из сообщений в localStorage — временное решение.**
   У браузеров есть лимит на объём localStorage (обычно 5–10МБ на сайт).
   Сжатие до 1200px по стороне сильно откладывает проблему, но не решает её
   полностью: при активной переписке с картинками лимит всё равно можно
   исчерпать. В боевой версии картинки должны загружаться в файловое хранилище
   (например, S3-совместимое или Яндекс Object Storage) и в сообщении
   храниться только ссылка на файл

### Как добавить новый модуль в план

Откройте `lib/modules.ts` и добавьте объект в массив `MODULES`:

```ts
{
  id: "vk_market",
  title: "Название модуля",
  phase: "traffic", // foundation | traffic | retention
  minBudget: "20to100",
  timeToResult: "2-3 недели",
  why: (a) => `Текст объяснения, можно использовать ${a.businessType} и другие поля ответов`,
  steps: ["Шаг 1", "Шаг 2", "Шаг 3"],
  score: (a) => {
    // чем выше число, тем выше приоритет модуля в плане; 0 или отрицательное — модуль не покажется
    let s = 5;
    if (a.goal === "leads") s += 2;
    return s;
  },
},
```

Это единственное место, которое нужно трогать, чтобы расширять экспертизу продукта —
не нужно лезть в UI.

## Интеграция подписки и оплаты (Россия)

Кратко сравнение вариантов под SaaS-подписку:

| Сервис | Плюсы | Минусы |
|---|---|---|
| **ЮKassa** | Самый распространённый агрегатор в РФ, понятная документация, поддержка рекуррентных списаний, подходит ИП и самозанятым | Комиссия зависит от оборота и категории, нужен договор |
| **CloudPayments** | Гибкий API специально под подписочную логику и сложные тарифные схемы, хорошо ложится на модель «тарифы + автосписание» | Порог входа чуть выше, нужнее техническая настройка |
| **Prodamus** | Проще всего внедрить — платёжная ссылка без глубокой интеграции, хорош для быстрого старта | Менее удобен для автоматического управления доступом внутри приложения по статусу подписки |

**Рекомендация для этого продукта:** начать с **ЮKassa** — она балансирует простоту
внедрения и наличие рекуррентных платежей (автоматическое продление подписки), а
поддержка самозанятых/ИП снижает бухгалтерские сложности на старте. Если позже
понадобится более гибкая тарифная логика (например, апгрейд/даунгрейд тарифа
пропорционально остатку периода) — можно посмотреть в сторону CloudPayments.

### Как это будет работать технически

1. Пользователь выбирает тариф → фронтенд создаёт платёж через API-роут
   (`/api/subscribe`), который на бэкенде вызывает API ЮKassa и создаёт объект
   `payment` с `save_payment_method: true` для последующих автосписаний
2. Пользователя редиректят на страницу оплаты ЮKassa
3. ЮKassa шлёт webhook на ваш эндпоинт (`/api/webhooks/yookassa`) о статусе платежа
4. Обработчик webhook обновляет статус подписки пользователя в базе данных
   (таблица `subscriptions`: `user_id`, `plan`, `status`, `current_period_end`,
   `payment_method_id`)
5. Отдельная задача по расписанию (cron / Vercel Cron) списывает деньги повторно
   по сохранённому `payment_method_id` перед концом периода

Middleware на защищённых страницах (`/dashboard/*`) проверяет
`subscriptions.status === 'active'` и `current_period_end > now()`.

### Рекомендуемый стек для следующего этапа

- **Auth**: NextAuth.js (email-магик-линк или пароль)
- **БД**: PostgreSQL (например, через Supabase или Neon) + Prisma ORM
- **Хостинг**: Vercel (нативно поддерживает Next.js) или VK Cloud / Yandex Cloud,
  если важно физическое размещение данных в РФ (152-ФЗ о персональных данных)
- **Уведомления**: Telegram-бот для писем о продлении/неудачном списании — аудитория
  предпринимателей активно пользуется Telegram

### Важно про 152-ФЗ

Так как вы работаете с персональными данными клиентов из России (email, телефон),
сервер и база данных должны физически находиться на территории РФ. Это стоит
учитывать уже при выборе хостинга — Vercel не подходит для боевого хранения
персональных данных пользователей, только для фронтенда/статики, если бэкенд с
данными будет вынесен на российский хостинг.
